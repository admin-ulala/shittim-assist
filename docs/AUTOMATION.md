# 自动化模块规划与编写入口

## 本次交付边界

本次完成领域划分、五个日常模块的**语义流程草案**、选项校验和流程执行器。它们描述“做什么、什么条件下做、怎样确认结果”，还不是可直接控制游戏的完整实现。

页面适配器 `DailyPageAdapter` 尚未实现，也未接入主界面或悬浮窗启动按钮。当前运行按钮仍然只做设备诊断。用户负责真实游戏流程验证；本次不执行游戏自动化。测试中的模拟适配器只验证调度契约，不能证明识图和流程正确。

## 内容分类

| 内容 | 子模块与扩展方向 | 本阶段 |
| --- | --- | --- |
| 清日常 | 咖啡厅、日程、社交、制造、商店、业务区、工作任务、桃信、邮件、每日奖励 | 前五项有流程草案；其余占位 |
| 推图 | 普通、困难、通缉悬赏、特别委托、学院交流会、活动本 | 占位 |
| 战术对抗赛 | 对手选择、次数限制、结果确认、领奖 | 占位 |
| 周期性战役 | 总力战、大决战、综合战术测试、无限制决战 | 占位 |
| 活动小游戏 | 按活动 ID 注册独立规则、有效期与资源包 | 占位 |

业务区是游戏导航入口，不再复制一套战斗逻辑。以后由业务区组合推图/PVP 子任务。

推图需要两个独立策略：`firstClear` 负责关卡解锁、编队、战斗与通关验证；`farm` 负责扫荡条件、次数、体力预算与奖励核对。普通/困难等是关卡类型，不与策略混成一个庞大开关。周期性战役应按模式和赛季分别配置，小游戏按活动注册；不复用不适合的日常固定步骤。

## 文件与分层

```
lib/automation/
  catalog.dart          模块稳定 ID、分类、实现状态
  model.dart            步骤、结果、页面适配器契约
  options.dart          五模块类型化选项与预算校验
  runner.dart           队列预检、取消检查、结果日志、遇错停止
  daily/
    cafe.dart           咖啡厅
    schedule.dart       日程
    social.dart         社交
    craft.dart          制造
    shop.dart           商店
```

调用方向：界面/悬浮窗 → 同一份计划和选项 → AutomationEngine → DailyRunner → 区服页面适配器 → RunContext → 识别/设备。

当前旧版 `AppConfig.selected` 保持原样，不将 `signin` 擅自迁移为社交签到，也不把 `daily` 猜测为工作任务或每日奖励。真正接入 UI 时升级配置版本，采用 `automation: {schemaVersion, order, modules}`；每个模块单独配置，并保留旧配置备份。PC 与悬浮窗应从同一模块注册表和字段定义生成控件，避免 Kotlin 另写一套模块配置。现在没有新增独立配置文件，避免与现有保存链冲突。

## 五个流程草案

### 咖啡厅

主页 → 确认一号店 → 处理来访列表 → 按选项领取收益 → 按学生名邀请一次 → 有界查找并摸头 → 可选二号店摸头 → 确认回到主页。

- `claimEarnings` 默认开启；摸头、二号店、指定邀请默认关闭。
- 每店最多识别六个学生、六个视角；页面适配器负责去重，不循环点击同一个标记。
- 邀请需要识别姓名、剩余邀请次数、两种确认弹窗；跨店邀请不能靠连续点两下代替状态检查。
- 收益为空需正向识别空收益状态；未找到领取按钮是未知，不能直接成功。

### 日程

主页 → 日程 → 按有序的区域/地点列表选择 → 确认详情及余票 → 执行 → 确认报告 → 下一地点 → 主页。

- 默认地点为空、票数上限零；地点不得重复且总数不超过票数预算。
- 学院列表最多翻三次。地点是否存在由区服资源表校验，领域层不锁死国服名称。
- 已完成需要正向标记；缺券返回 exhausted，停止整个队列，不购买日程券。
- 好感动画需要独立识别分支；超时不能当作“已经做过”。

### 社交

主页 → 社交 → 小组 → 识别签到弹窗或已签到证据 → 必要时确认 → 验证今日签到 → 主页。

- 无小组返回 unavailable；未识别到弹窗与已签到是不同结果。
- 不加入/退出小组、不操作好友列表。

### 制造

主页 → 制造 → 识别三个槽位 → 按槽领取已完成品 → 可选使用已保存配方快速制造 → 主页。

- 槽位必须区分完成、制造中、空位、未知；未知不能当作空位。
- 默认仅领取完成品，不用加速券；不沿用 MaaBa 的整批领取确认逻辑。
- 快速制造默认零次；最多三次，每次一颗制造石，须有明确预算、空位和已保存配方。
- 每次提交前后检查槽位、材料，确认失败不自动重试投入。

### 商店

主页 → 常规商店 → 根据商品 ID 清单选定商品 → 核对商品、数量、币种及总价 → 购买一次 → 核验购买结果 → 主页。

- 默认清单为空、预算零；只支持信用点，预算约束整笔交易。
- 不使用“筛选后全选”，不刷新商店，不购买青辉石商品。
- 价格或币种无法识别即停止；购买确认后结果不明时保留证据，不重试。

## 页面适配器怎样编写

实现 `DailyPageAdapter` 并在 `supportedOperations` 声明已完成的操作。执行器会预检整个队列，缺少任何操作时在第一步之前拒绝运行。

每个 `execute(step)` 必须：

1. 检查 RunContext 的暂停/取消和期限；核对目标包名。
2. 获取当前新截图，识别 `before` 页面；读取必要的券数、材料或报价。
3. 在局部 ROI 中识别目标，将参考位置通过 ScreenGeometry 映射。宽高比不匹配要求显式内容区域。
4. 通过 RunContext 发送输入，输入本身不重试；每次后续点击前重新识别。
5. 有界等待并确认 `after`，返回 completed/alreadyDone/exhausted/unavailable/unknown。

`before`/`after` 是语义检查条件，不是单张图片文件名。例如 `craft.confirmedEmptySlot` 包含页面、槽位状态与资源检查。每个复合操作完成后必须收起本操作弹窗并回到下一步可识别的模块页面；`navigation.home` 则正向验证主页。

`saveFailureEvidence` 只保存本地截图及识别信息，遵守取消/超时，不进行额外游戏操作。未知结果抛错并终止；缺券或功能未开放会返回非成功报告并停止队列。调用者必须展示报告，不能把引擎函数正常返回等同“所有日常成功”。没有开启的操作返回空计划，可视为无需执行。

实际接入时必须由 AutomationEngine 持有设备锁并传入同一个 RunContext；适配器内部所有等待也使用该 context。当前契约不强行取消任意 Future，因此不能实现无期限等待。
